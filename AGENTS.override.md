# This Herdr setup

This folder is the Herdr app's home and also a git repository of the owner's customizations.

**Read `AGENTS.md` in this folder in full before changing anything, unless it is already in your context.** It is Herdr's manual for the installed version. Herdr rewrites it on every start, so never edit it: notes about this setup belong in this file and in `docs/agents/`.

Why this file has this name: Codex reads one instruction file per folder and prefers `AGENTS.override.md`, so it gets these notes and the pointer above. Claude Code gets both files through the imports in `CLAUDE.md`.

## What is custom

The mod sources are under `packages/<feature>/mods/<name>/`. Herdr reads real copies under the ignored `mods/`, alongside its shipped mods.

**Before changing a mod, or saying how it works, read its notes in full.** They are not loaded with this file. Each says what the mod is, what each of its files does, where its state lives, how to try it, and the behavior to preserve: what must keep working, why it is built the way it is, and what was and was not tried by hand.

- **Hide names** is a mode of the whole window, not one mod: `spaces-sidebar`, `mark-agents-unread`, `agent-usage`, `back-and-forward` and the four clones above draw made-up names while shared `names.hidden` is set. Read `docs/agents/hide-names.md` before changing where any of them draws a name.
- **Files kept the same in several mods**, since a mod imports only from its own folder: `alias.js` (in `hide-names`, `tabs-names`, `pane-names`, `toast-names`, `spaces-sidebar`, `mark-agents-unread`, `agent-usage` and `back-and-forward`), `fieldkeys.js` (in `file-editor`, `project-search` and `go-to-file`), `remote.js` (in `file-editor` and `project-search`), `external-apps.js` (in `file-explorer`, `project-search` and `spaces-sidebar`) and `git-guard.js` (in `git-panel` and `git-diff`). Change every copy together. `python3 docs/check-shared.py` verifies all five families before each push.
- **Keep the notes true.** A change to what a mod does, to where its state lives or to something under its "Behavior to preserve" goes into its notes in the same change. A note about one mod goes in its file, not here; a new mod gets a file and a row in the table.
- **Layout `herdr-powertools`** (`layouts/herdr-powertools.json`): a clone of Herdr's `main` (from version 0.1.18). The differences: its `spaces` block shows the mod `spaces-sidebar`, its `agents` block shows the mod `mark-agents-unread`, its `files` block shows the mod `file-explorer` and its `changes` block shows the mod `git-panel` (the block keeps its id, so the tab bar’s Git button opens it); the panel's stack has a third child, `search`, which shows the mod `project-search`; the `work` column ends with `search-keys`, a block 0 px tall with a second copy of `project-search` that only takes a key; and its root has `link_handlers: ["editor-links"]` (Herdr added it when it first saw that mod). The sidebar has a block of its own between `brand` and `sidebar-lists`, `usage-side` (62 px, the mod `agent-usage` with props `{ role: "side" }`). Its `tabs` block shows the mod `tabs-names`, the tab block's pane frame has the header `pane-names`, and its `status` block shows `hide-names` (each block keeps its id), and its root has `"toast": "toast-names"`, which draws every notification: Herdr's own, with hide names (see `docs/agents/hide-names.md`). The status bar has no usage figures: they were taken out, since the widget shows them. Its look adds, since 0.1.18: a `veil` of 0.3 on the tab block's pane frame (the panes you're not in fade, mod panes too) and an `accent` hover color on the root's divider.

The 28 px status row places Spotify Mini, Back and Forward and the Quick Actions launcher to the right of the `status` block. All three ship with the full layout.

Edit code and assets under `packages/`. Package shortcuts are generated from the root `keys.json`. The gallery previews and README cover take their titles from the recipes and their captions and screenshot crops from `docs/gallery-cards.json`. After changing a distributed file, run `python3 docs/gallery.py` and verify with `python3 docs/gallery.py --check`.

## Working here

- Run `python3 docs/sync-mods.py` to sync the checkout's live mod copies, or keep `python3 docs/sync-mods.py --watch` running while editing. The script uses `rsync` and mirrors each packaged mod's files, including deletions, while preserving Herdr's generated typings and config. A separate app home can be synced with `--home PATH`. After syncing a change run `herdr-app check mods/<name>` and `herdr-app status`, and look with `herdr-app shot`.
- The repository's git hooks are in `.githooks/`, turned on per clone with `git config core.hooksPath .githooks` (this one has it). `post-merge`, `post-checkout` and `post-rewrite` (a rebase) run the sync, so a pull never leaves Herdr on old copies. `pre-push` refuses a push when `mods/` is not what `packages/` holds (`sync-mods.py --check`: sync, try it in Herdr, then push), when shared helpers differ, when the tests (`*.test.mjs`, under `node --test`) of a package the pushed commits change fail, or when `docs/gallery.py --check` finds stale files. It checks the files in the checkout, and says so when `packages/` has changes not committed. Don't skip it with `--no-verify` unless the owner asks. The usage tests take about 20 seconds.
- Before launching a test or screenshot Herdr on macOS, use a short scratch path, a short `TMPDIR` and a short, unique `HC_SESSION`. The Unix socket path can be at most 103 bytes. Check `hc server status --json` with the sandbox's environment before opening its window. If the computed path is still too long, use a short, sandbox-specific `HC_SOCKET` under `/tmp` and pass it to both Herdr and the sandbox CLI.
- Pointer drags and typing cannot be driven from a shell. Say so when a change to those paths was not tried by hand.
- A menu, a dialog or a request can be driven from a shell with a throwaway mod: `mod.json` `{ "place": "none", "overlay": { "width": 60, "height": 30 } }`, opened with `herdr-app do mod.open --name <mod>`, whose `init` reads a JSON file and calls `openOverlay(...)` or `setShared("file-explorer.request", ...)`, then closes itself. A request carries its own `root`, so the live panel runs it against a scratch folder. A mod can only import from its own folder: copy the modules it needs into it. Every overlay takes the keyboard from the owner while it is open, so keep these runs few and short, and delete the mod afterwards (`.gitignore` never tracks it).
- `cx.spawn(body)` runs `body` up to its first `await` at once. Called from `render()`, that first step is inside the draw: `cx.notify()` there is refused and ends the task without a word. A task begun in `render()` that does more than read should `await` first.
- `herdr-app shot` shows no focus ring and no selection in the editor while Herdr is not the active app.
- Write a new runtime mod's `mod.json` before anything else in its folder. A folder Herdr first sees without one is docked into the shown layout by itself, as a new block at the end of `layouts/herdr-powertools.json`: take that block out again.
- Syncing a file under `mods/` reloads mods and cuts off their running tasks, also those of a mod that was not saved. Wait a few seconds after a sync before sending a request, or it is taken and never answered.
- After an `await`, `props()` may answer for another copy (the one that drew last). Read it in `init` or `render` and keep what it said.
- `herdr-app check` shows nothing a mod logs. To time code in Herdr's own engine, make a throwaway mod whose `init` does the work and throws an `Error` with the timings as its message: the check prints it. `init` is stopped at 500 ms like an event handler, so time a few things a run. `node` is many times faster and says nothing about it.
- An overlay opened for a test is closed with `herdr-app do overlay.close` (the top dialog or popup), or `--id o<n>` for a window: the ids count up from `o1`. A window is closed by opening another under its `key` and closing the id that returns: `overlay.close --id` with a guessed id answers `ok` whether or not it closed anything.
- Keys in a mod's text fields. A field (and the editor's text) binds Up, Down, Tab, Cmd+F and more, and passes nothing on, so a binding has to sit as deep as the field to win. Up to Herdr 0.1.16 a `keys.json` section called `mod:<x> > Input` did that, because Herdr pasted the name into a key-context expression. Since 0.1.17 (`src/keys.rs`, `tab()`) a section's name is one literal mod name: such a section is still valid and listed by `keys()`, binds nothing, and writes no `keys.error`. So `go-to-file`, `project-search` and `file-editor` install that section's keys themselves with `cx.bind_keys`, under the context `mod == <x> > Input` and with the same actions (`fieldkeys.js`). Herdr runs every script action at the window root (`run_action`), as it runs one from `keys.json`, so the command reaches `nextCommand()` unchanged. Herdr drops all bindings whenever `keys.json` changes and puts back only its own: the mods bind again when `keys()` changes, from `render()` through a task (binding is refused in `render()`).
- What people read: `README.md` is the tour (a picture and a few lines for each feature, the keys to copy, Install), and `docs/<feature>.md` is each feature's whole reference. A change to what a feature does goes into its page, and into the README only when the tour's few lines are no longer true. Say a thing once: what holds for every feature is in the README's "The same everywhere".
- The pictures in `docs/images/` are the real app, shot with `herdr-app shot` in a sandbox, never the owner's window: a second Herdr with its own core, home and fake projects. No real project, session or machine name may show in them: `herdr-app` is the one real name allowed. `docs/screenshots/retake.sh` takes them all again from nothing, and `docs/screenshots/README.md` says how they are made, how to change or add one, and what trips the staging up: read it before touching a picture. After a change to how a mod looks, retake the pictures it is in (`./shoot.sh <step>`, then `./make.sh <name>`), and keep that folder's scripts working: they are how the pictures stay true.
- When a question is about how Herdr delivers an event or a key, read its source at the installed version's tag instead of guessing: the GPUI fork is under `vendor/gpui-pre`, the script bridge under `vendor/gpui-kit/crates/shell`.
- After Herdr updates (`herdr-app --version` newer than the version named under "What is custom"), follow `.claude/skills/herdr-update/SKILL.md`. It holds the whole check: the clones against their originals, the changelog and the source, sorted against this setup, with a report for the owner. What each check found, and what is still open, is logged in `checks.md` beside it. The clones get no update from Herdr, so this is how they keep up.

## Git

- `.gitignore` is an allowlist: new sources under `packages/<feature>/mods/` are already allowed. Add an entry for a new layout, theme or root file.
- **This repository is public. Before every commit, read the staged diff (`git diff --cached`) and make sure it holds nothing that should not be public:** no secrets, tokens, passwords, API or SSH keys; no personal information (names, email addresses, phone numbers, addresses); no home or project paths (`/Users/...`, `/Volumes/...`), machine or host names, client or project names; nothing else private or security-sensitive. This applies to every committed file, including settings, key bindings, notes, screenshots and commit messages. If something like that is needed locally, keep it in an ignored file. The deliberate exceptions: the owner's name in the `NOTICE` copyright line, and the author name and email that git takes from its own config for a commit. The owner's email address must never appear in any file. If you are unsure whether something is safe to publish, stop and ask before committing.
- Never track state: `shared.json`, `view.json`, `data/`, `layouts/.state/`, or anything Herdr ships. State holds space names, folder paths and project names.
- Commit messages follow Conventional Commits: `<type>(<scope>): <description>`, then an optional body and footers.
